# Story directing is our "Working Directory"

# Staging Area: In order to have git track the changes to files in our "working directory" -- they are added to the Staging area,
And that is basically an intermediate place where you can pick and choose which files inside your working directory that you want to commit

    -git status: shows you what files are in the staging area
        -- untrack files are in red -- the files are in the working directory but not yet staging area
        -- committed files are in green and are ready to be "committed" to the repository (version control)

    -git add <filename> or . to add all files listed: will put untracked files in the staging area so changes are tracked

    -git commit -m: "m" for the commit message - message is very important to help you identify or track what changes were made in each "commit" -- a Safe Point

    -git log: shows what you have committed to version control

    -git checkout <filename>: revert changes locally in the working directory (rollback to the previous version --- aka safe point)

    -git diff: compare changes between in version of a file

# Remote repository (like GitHub)

    *** Must tell your local git repository where your remote repository is
        -- first add the remote repository reference to your local with the following command

        -git remote add origin <remote_url>  <-- origin is the name of your remote repository. Theoretically, it can be any name, but industry convention is to leave it as "origin"
            -- then you want to PUSH your local repo up to your remote with the "push" command

        -git push -u origin <branch_name> : the -u flag is used to link up the remote and the local repos
            -- origin is the name of the repo and the branch name is the branch within the repo

# To remove files from the staging area (after you have peformed a git add . or filename
    -git rm --cached -r .:   rm==remove, -r==recursively, .==all files

# Clone a remote repository

# BRANCHING:
    -git branch branch-name :commit to an experimental branch. a way to test code without messing up the main project (main branch)
    -git checkout branch-name: to switch branches

# MERGING:
    -git merge branch-name: merge the feature or experimental branch with the main branch (main project). must be on the branch you want to merge the feature into

# REBASE
    -git rebase branch-name: another way of combining work between branches. Rebasing essentially takes a set of commits, "copies" them, and plops them down somewhere else.
        --The advantage of rebasing is that it can be used to make a nice linear sequence of commits. The commit log / history of the repository will be a lot cleaner

# MOVING AROUND THE COMMIT TREE

    -HEAD: HEAD is the symbolic name for the currently checked out commit -- it's essentially what commit you're working on top of.
        HEAD always points to the most recent commit which is reflected in the working tree. Most git commands which make changes to the working tree will start by changing HEAD.
        Normally HEAD points to a branch name (like bugFix). When you commit, the status of bugFix is altered and this change is visible through HEAD.

        Detaching HEAD just means attaching it to a commit instead of a branch. If commit was C4 and Branch was BugFix
        the command "git checkout C4" would result in a detached head

# RELATIVE REFS
    - relative refs allow you to specify enough characters of the hash to uniquely identify it without specifying the entire hash
        ex: fed2da64c0efc5293610bdd892f82a58e8cbc5d8 can be identified with just "fed2"
    -git log: command to see teh commit tree and see the commit hash values

    With relative refs, you can start somewhere memorable (like the branch bugFix or HEAD) and work from there.

    Relative commits are powerful,  two simple ones are: ^ (caret) and ~ (tilde)
        -git checkout HEAD^
            --Moving upwards one commit at a time with ^: Each time you append that to a ref name, you are telling Git to find the parent of the specified commit
            So saying main^ is equivalent to "the first parent of main". main^^ is the grandparent (second-generation ancestor) of main. You can also reference HEAD as a relative ref.
            --Moving upwards a number of times with ~<num>: The tilde operator (optionally) takes in a trailing number that specifies the number of parents you would like to ascend. Let's see it in action.

    - BRANCH FORCING: common way to use relative refs to move branches around
        -git branch -f main HEAD~3: moves (by force) the main branch to 3 parents behind HEAD
        -Note: In a real git environment git branch -f command is not allowed for your current branch.

# REVERSING CHANGES IN GIT
    --There are two primary ways to undo changes in Git -- one is using git reset and the other is using git revert
    And just like committing, reversing changes in Git has both a low-level component (staging individual files or chunks) and a high-level component (how the changes are actually reversed)

    -git reset branch-name or HEAD~<num>: reverses changes by moving a branch reference backwards in time to an older commit. In this sense you can think of it as "rewriting history;"
        -git reset will move a branch backwards as if the commit had never been made in the first place.

    While resetting works great for local branches on your own machine, its method of "rewriting history" doesn't work for remote branches that others are using.
    In order to reverse changes and share those reversed changes with others, we need to use git revert. Let's see it in action.
    -git revert branch-name

# CHERRY PICKING
    -git cherry-pick <commit1> <commit2> <...>
    It's a very straightforward way of saying that you would like to copy a series of commits below your current location (HEAD)

# INTERACTIVE REBASE
    - cherry-pick command is great when you know the commit you want to add below HEAD.  Use interactive Rebase when you don't know the commit(s)
    you want to add. With Interactive Rebase you can review a series of commits your about toe rebase

    -All interactive rebase means is that Git is using the rebase command with the -i option.
     git will open up a UI to show you which commits are about to be copied below the target of the rebase. It also shows their commit hashes and messages, which is great for getting a bearing on what's what.
     -git rebase -i HEAD~4

# GIT TAGS
    a way to permanently mark historical points in your project's history. For things like major releases and big merges,
    they (somewhat) permanently mark certain commits as "milestones" that you can then reference like a branch.
    More importantly though, they never move as more commits are created. You can't "check out" a tag and then complete work on that tag
    -- tags exist as anchors in the commit tree that designate certain spots.

    -git tag tag-id branch-name: if branch-name left-off, git will add tag at HEAD


# GIT DESCRIBE
    Git describe can help you get your bearings after you've moved many commits backwards or forwards in history;
    this can happen after you've completed a git bisect (a debugging search)

    -git describe <ref>: ref is anything git can resolve into a commit.
    If you don't specify a ref, git just uses where you're checked out right now (HEAD).
    The output of the command looks like:

    <tag>-<numCommits>-g<hash>

    Where tag is the closest ancestor tag in history, numCommits is how many commits away that tag is, and <hash>
    is the hash of the commit being described.
